# 日志、监控和事故处理

## 上线配置

1. API 设置 `LOG_FORMAT=json` 和合适的 `RUST_LOG`，日志平台采集容器标准输出。
2. Prometheus 使用 `deploy/monitoring/prometheus.yml` 从 Docker 私网抓取 `api:8080/metrics`。公网 Caddy 已对 `/metrics` 返回 404。
3. 将 `deploy/monitoring/alertmanager.yml.example` 复制到部署密钥目录，替换为真实的值班通知 Webhook；不得把 Webhook 提交进 Git。
4. 触发一次测试告警，确认故障和恢复通知都能到达至少两名值班人员。

每个 HTTP 响应都带 `x-request-id`。日志记录同一个 `request_id`、方法、路径、状态码和耗时，客户报错时先索取该编号。指标仅含请求数量、5xx 数量、并发量和累计耗时，不包含会话内容或客户业务数据。

## 事故分级

- P0：数据不可恢复、密钥泄漏或全部客户不可用。立即停止发布、隔离影响面并通知负责人。
- P1：授权、计费或主要模型调用大面积异常。15 分钟内响应并开始通报。
- P2：部分功能降级或单一上游异常。工作时间内跟进并提供绕行方案。

## 处置顺序

1. 记录开始时间、告警、发布版本和 request_id，指定事故负责人。
2. 检查 `/readyz`、容器健康、PostgreSQL、Redis、最近迁移和上游状态。
3. 采用可逆措施止损；涉及金额时先暂停相关写入，禁止直接改余额或删除流水。
4. 每 30 分钟更新影响、进展和下一次更新时间。
5. 恢复后验证授权、模型调用、用量结算、线下收款登记和余额对账。
6. 两个工作日内完成复盘，记录根因、时间线、影响、补救和责任人。
