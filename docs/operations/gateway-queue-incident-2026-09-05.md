# 2026-09-05 网关排队超时与任务进度缺失

## 已确认的原因

故障请求：`fdf1f776-ff49-4023-abd3-eb58864a56bf`。

以下时间为北京时间，证据来自生产 API 容器日志、只读用量查询与本机 Codex 会话记录。

- 模型为 `gpt-5.6-sol`，推理强度为 high，通过 `alpha-gateway` 调用。
- 主任务与三个子任务共用一个 run。网关按 run 串行执行请求，保证每次模型调用完成结算后再处理下一次请求。
- 主任务最后一次请求在 **12:19:40** 返回 HTTP 429，网关日志耗时 **180110.56 ms**，对应固定的 180 秒排队上限。
- 前序请求随后在 **12:19:43** 正常结算，HTTP **200**，耗时 **178534 ms**，记录 **13265 个输出 token**。这次排队失败不能归因为上游 LLM 限流。
- 固定排队上限把多个前序请求的等待时间累计计算，正常的长生成也会使后面的请求提前失败。
- 桌面 UI 会在消息中有正文或工具内容时隐藏旧的 `Reconnecting... n/m` 块；主任务等待子任务时，也缺少整个 run 的实际输出进度。

## 修复行为

1. 保留每个 run 的 FIFO 顺序和串行结算。每当前序请求完成，刷新后续等待者的期限，且不重新入队。单个前序请求允许的等待时间覆盖配置的模型请求超时、最多五次重试及结算余量。
2. 原生 Responses 收到终止事件后立即结算和释放队列，不继续等待可选的 `[DONE]` 或 HTTP EOF；终止事件仍在结算之后才发给客户端。
3. 新增需要任务 token 的 `GET /v1/run-status`，只返回该 run 的活动状态、等待请求数、最近收到模型数据的时间，不返回提示词、输出正文或凭据。
4. 桌面客户端每 5 秒查询网关状态，只有状态或真实输出时间变化时才产生进度事件。查询失败不会影响推理；旧后端返回 404 时自动停止查询；任务退出时取消查询。
5. 正文之后仍能显示重连次数、推理阶段、模型输出与排队情况。补充无独立 error 事件的失败结束通知，并忽略旧 run 的迟到事件及其他线程的结束通知。
