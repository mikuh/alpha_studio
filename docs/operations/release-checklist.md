# 发布检查清单

## 合并前

- CI 中前端、后台、Tauri 的格式、Clippy、测试和构建全部通过。
- 每周依赖审计没有未评估的高危漏洞；升级 PR 经过测试后合并。
- 数据库迁移已在 staging 的生产数据副本上演练，且迁移前备份通过恢复演练。
- 协议版本、隐私说明、模型价格和第三方接收方与本次版本一致。

## Staging

1. 使用 `deploy/staging.env.example` 建立由密钥管理服务注入的 staging 配置；使用与生产相同的镜像、配置结构和迁移命令部署。推送 `v*` 标签会把 API 和后台镜像发布到 GHCR。
2. 执行 `BASE_URL=https://staging.example.com npm run smoke:staging`。
3. 人工完成一次激活、重新启动、离线启动、授权恢复、模型调用、用量结算、线下收款登记和差错更正。
4. 确认余额对账为“一致”，日志能按 `request_id` 检索，测试告警能到达值班渠道。

## 生产发布

- 记录镜像摘要、Git 提交、迁移版本、负责人和回滚版本。
- 先备份并运行恢复演练，再执行迁移；禁止未经备份直接变更生产数据库。
- 分批发布 API 和后台，运行冒烟测试后再发布客户端。
- 观察错误率、延迟、授权和账务对账至少 30 分钟。

回滚应用时不得回滚或手工删除已经写入数据的数据库迁移；使用向前修复迁移。涉及金额异常时暂停写入并保留所有流水。
